本ドキュメントは「d次元 Apriori-Window」が既存研究群の中でどのような位置にあるかを整理したものです。

## 1. 本研究が答える問い

> 「d次元グリッド上のトランザクションデータにおいて、
> スライディングウィンドウ内サポート ≥ θ となる
> 全アイテムセットパターン P と、その密集ウィンドウ開始点集合 L_θ(S_P) を厳密列挙せよ」

出力は「**何が（パターン）× どこで（密集領域の位置）**」の組であり、
これを全パターンについて厳密・網羅的に求めることが本研究の問題設定。

## 2. 研究系譜と本研究の位置

本研究は2つの系譜の**交点**に位置する。

```
【系譜A】トランザクションパターンマイニング
  Apriori (Agrawal '94)
      │ アイテムセット単調性による枝刈り
      ↓
  FIM / FP-Growth
      │ グローバルサポート → 局所密集に対応できない
      ↓
  出現間隔ベース手法 (LPFIM / LPPM / Recur)
      │ 局所密集区間を出力できる
      │ ただし「連続する出現の間隔」に依存（線形順序前提）
      │ → 多次元化不可能（後述）
      ↓
  Apriori-Window (高橋論文) ← 直接の前身
      │ スライディングウィンドウの出現数を直接評価
      │ ストライドジャンプ + Apriori 枝刈り
      │ 1次元（時間軸のみ）
      ↓
  【本研究】d次元 Apriori-Window
      任意の d 次元グリッドに拡張

【系譜B】密ブロック検出（テンソルマイニング）
  CrossSpot (SDM'15)
      │ テンソルの密ブロックを greedy 検出
      ↓
  M-Zoom (ECML'16) / D-Cube (WSDM'17)
      │ 品質保証付き・ディスクベース
      │ d次元テンソル対応・上位k個
      ↓
  CatchCore (ECML'19) / SpecGreedy
      │ 階層的密コア・スペクトル手法
      │ アイテムセット列挙には O(2^|I|) 回の独立実行が必要
      ↓
  【本研究との接点】
      最も問題設定が近い先行研究だが、
      アイテムセット列挙を効率的に行う機構を持たない
```

## 4. 出現間隔ベース手法（LPFIM系）を多次元化できない理由

### LPFIM / LPPM / Recur の設計原理

これらは「連続する2出現のタイムスタンプ差（出現間隔）」を評価することで密集区間を推定する。

```
LPFIM:  gap = ts_i - ts_{i-1} > minthd1 → 区間を分割
LPPM:   surPer(ts_i) = interval(ts_i) - maxPer を累積し maxSoPer で区間終了
Recur:  recur_per 以内の連続出現をまとめて1周期区間とする
```

共通の構造：**「出現タイムスタンプ列を線形に走査し、連続する2出現の間隔を評価する」**

### 多次元化が不可能な本質的理由

```
1次元: occ(P) = {3, 7, 15, 22, ...}
       → 自然な線形順序がある
       → 「次の出現」が一意に定まる
       → gap = ts_{i+1} - ts_i が定義できる

d次元: occ(P) = {(1,3), (2,1), (1,5), (3,4), ...}  （2D の例）
       → 線形順序がない（どの出現が「次」？）
       → gap の定義が一意に定まらない
       → minthd1・surPer・recur_per の意味が崩壊する
```

さらに高橋論文は、LPFIM系には**1次元でもすでに構造的欠陥**があると指摘している。

> 「ギャップパラメータがパターン同定精度と区間検出精度の両方を支配するため、
> 両者を同時に高く保つ適切なパラメータ設定は一般に存在しない」

多次元化する以前に、1次元での精度上の限界もある。

### Apriori-Window が多次元化できる理由

```
Apriori-Window の評価:
  sup(P, l, W) = |{t ∈ occ(P) | l ≤ t < l+W}|
  「出現間隔」ではなく「矩形窓内の出現数」を直接数える

d次元への拡張:
  S_P(s) = |{b ∈ occ(P) | s_k ≤ b_k < s_k+W_k, ∀k}|
  「矩形窓」を「d次元矩形窓」に拡張するだけで概念が成立する
```

「連続する出現の間隔」は線形順序依存だが、「矩形窓内の出現数」は線形順序を必要としない。

## 5. MZoom をアイテムセット方向に拡張しない理由

「MZoom をアイテムセット対応にすれば同じことができるのでは？」という問いへの答え。

### 拡張を試みると何が起きるか

```
手順: パターン P ごとに二値テンソル I_P を作り MZoom を実行する

P = {A,B}   → I_{A,B}[b] = 1 if {A,B} ⊆ tx at bin b → MZoom 実行
P = {A,C}   → I_{A,C}[b] → MZoom 実行
P = {B,C}   → MZoom 実行
...
P = {A,B,C} → MZoom 実行
```

### 問題1：指数爆発

```
|I| = 20 → 2^20 ≈ 100万回の MZoom 実行
|I| = 34（Chicago Crime）→ 2^34 ≈ 170億回
```

Apriori 枝刈りがないため全アイテムセットを独立に実行する必要がある。

### 問題2：Apriori 枝刈りと MZoom の設計的非互換

Apriori 枝刈りは「複数パターンの結果を連携させる」ことで成立する。

```
L_θ(S_P) ⊆ L_θ(S_Q)  （Q ⊂ P のとき）
→ P の密集領域は Q の密集領域の部分集合
→ Q に密集領域がなければ P も探索不要
```

MZoom の各実行は独立した密度最大化問題であり、
他のパターンの実行結果を参照する設計になっていない。
Apriori 枝刈りを統合するには MZoom のコアアルゴリズムを根本的に再設計する必要があり、
**その再設計の結果は事実上 Apriori-Window になる**。

### 問題3：出力形式の意味論的不一致

```
MZoom の密ブロック（各次元で任意の値集合）:
  時間次元: {1, 5, 20, 47}  ← 非連続でよい
  x 次元:   {2, 3, 7}

本研究が求めるもの:
  連続スライディングウィンドウ [l, l+W) の密集開始点集合
  → 「いつ・どこで密集していたか」という連続した時空間領域を表現する必要がある
```

「MZoomをアイテムセット方向に持ってくる」試みをすればするほど Apriori-Window に収束する。
これは本研究の設計が MZoom の未解決問題を正しい方向で解いていることの傍証でもある。

## 6. 各比較手法との関係サマリ

| 手法 | 本研究との関係 | 比較の正当性 |
|------|--------------|-------------|
| **Apriori-Window 1D** | 直接の前身（1D → dD 拡張） | 前身研究、比較対象ではなく基盤 |
| **MZoom / D-Cube / CatchCore** | 最も問題設定が近い先行研究系譜 | 主要比較手法。アイテムセット列挙コストの差を示す |
| **Colocation / STCP-Miner** | 空間的近傍共起（別定義）だがパターン精度は比較可能 | 近似比較手法。問題設定の違いを論文内で明示する必要あり |
| **ST-DBSCAN** | 全く別パラダイム（ε近傍クラスタリング） | 参考比較。F1=1.0 が自明になる評価設計の問題あり（要修正） |

| **LPFIM / LPPM / Recur** | 多次元化不可能な手法群 | 比較対象外。「なぜ採用しないか」の説明材料 |

## 7. 論文 contribution の核心（この地図から導かれる narrative）

### 空白地帯の発見

既存研究は「アイテムセット列挙」と「時空間密集領域検出」を同時に・厳密に・効率的に行う手法を持たなかった。

- 出現間隔ベース手法（LPFIM系）: アイテムセット列挙はできるが、多次元密集領域を定義できない
- MZoom族: 密集領域は検出できるが、アイテムセット列挙には O(2^|I|) コストがかかる
- この「両方できる」領域が空白だった

### 本研究が空白を埋める方法

Apriori-Window の3要素技術（出現リスト+二分探索、ストライドジャンプ、候補区間交差枝刈り）を
d次元に正しく拡張・統合することで、アイテムセット列挙と密集領域検出を単一フレームワークで実現。

```
アイテムセット列挙コスト: O(M)  ← Apriori 枝刈りにより M << 2^|I|
密集領域計算コスト:       O(G)  ← d次元接頭辞和により O(1)/クエリ
```
